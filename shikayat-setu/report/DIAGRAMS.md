# Diagram notes — Campus Shikayat Setu

The college's report sequence lists an ER diagram, use-case diagram, class diagram, activity diagram, deployment diagram and module hierarchy. These diagrams describe the implemented application, not a proposed rewrite. Their editable `.drawio` sources were generated programmatically; they are diagrams.net documents, not manually drawn StarUML or EdrawMax files. The six indexed diagram types are specified in `build_corrected_diagrams.py` and their PNGs are exported from those editable documents using the diagrams.net web engine. The separate architecture image is maintained separately.

## Reading the figures

- **ERD:** The three pages in `fig-erd.drawio` use Chen-style rectangles, relationship diamonds and selected attribute ovals. Underlined `id` is the key. `(min,max)` denotes the number of relationships in which an instance of the adjacent entity participates; `N` means many. Together they cover the schema's eight foreign keys; the department–complaint relationship is repeated for context. Refer to report section 3.3 for all columns and constraints. User department and event actor are nullable. Each complaint has at most one feedback row. Separate assigned department and category permit administrative reassignment.
- **Use case:** Four pages for Student, Officer, Administrator and Public visitor. Only the first three are stored user roles. Each page has one actor symbol. The admin can also perform officer actions. Its feedback route accepts admin requests but there is no admin feedback form in the interface. Public tracking normally requires a complaint code and matching roll number.
- **Class:** Two pages form a conceptual domain model covering all eight schema associations and multiplicities, not a claim that the project defines Python ORM classes. It does not invent operations.
- **Activity:** Five unpartitioned UML activity pages cover submission, officer/admin resolution, student feedback, student reopening and admin force-close. Arrows are control flows, not partition boundaries. Rejection and stale-update paths are shown separately; no concurrency or automatic continuation between separate activities is implied. Acknowledgement and starting work are optional before resolution. The reopening code checks whole-day age, and force-close does not enforce a waiting period.
- **Deployment:** A local single-computer demonstration of a browser, Python/Flask environment and SQLite file. LAN access is optional and depends on local settings. The server is not a production deployment.
- **Module hierarchy:** Project files grouped by responsibility; the lines indicate grouping rather than direct imports. There are no Flask blueprints or background workers.

`Campus_Shikayat_Setu_Project_Diagrams.pdf` and its DOCX companion provide 16 larger, separate A4 pages for viewing or printing, with portrait orientation for tall activity diagrams. Use this collection when small diagram labels need closer inspection; the main report diagrams have also been enlarged within its A4 pages. The report still contains the diagrams and descriptions under the required index sections. Diagram elements in the Word document are images; edit the `.drawio` files to change individual shapes.

## Editing and rebuilding

1. Open the `.drawio` files in diagrams.net (desktop or web). `fig-erd.drawio` has three pages; `fig-usecase.drawio` has four, `fig-class.drawio` has two, and `fig-activity.drawio` has five. Connectors are attached to shapes, but their intermediate bends and separately positioned labels do not automatically rearrange. Some visual boxes use several independent shapes/text objects: select them together, then recheck layout and relationships after editing.
2. Programmatic rebuilding overwrites generated sources. To rebuild all six indexed sources, run `python report/build_corrected_diagrams.py` from the project directory. To rebuild all seven editable documents, run `python report/build_drawio.py`; it does not export PNGs.
3. PNG export uses the actual diagrams.net web engine through `render_drawio.js`. For the recorded Linux rendering environment use Node.js 22+, a checkout of [draw.io v32.7.4](https://github.com/jgraph/drawio/tree/v32.7.4), and `npm install --prefix /path/to/render-deps puppeteer-core@25.18.1 @sparticuz/chromium@153.0.0`. Set `DRAWIO_WEBAPP` to the checkout's `src/main/webapp`, set `NODE_PATH=/path/to/render-deps/node_modules`, and run `node report/render_drawio.js` (or append `fig-activity` to export just the activity pages). Chromium's system libraries (including NSS/NSPR) must be available. The renderer is intended for Linux x86-64; alternatively export each page from diagrams.net at 150% on other systems. Do not use the old Python SVG renderer: its output differs from diagrams.net.
4. Run `python report/build_diagram_collection.py`, `python report/build_usecase_pdf.py` and `python report/build_usecase_docx.py`. Rebuild the project report PDF and DOCX as described in `REPORT_FORMAT.md`, using a disposable seeded database. Run diagram and report validators, visually review every page and check Word pagination before submission.

The generator checks the SQLite schema's eight foreign keys, feedback uniqueness and optional relationship columns. It cannot replace an independent review of visual notation, code behavior, and college-specific requirements.
